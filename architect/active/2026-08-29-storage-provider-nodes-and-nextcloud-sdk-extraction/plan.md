# Design and Implementation Plan

Completed platform slice: steps 1 through 4 are implemented as separate `@McpTool`/`@McpService` metadata, typed resolver selection, direct service-parameter injection, and `services/list` discovery. The remaining steps govern authorization and provider extraction.

1. Keep callable nodes under `@McpTool`; use `@McpService` only for provider-node classes and service parameters. Do not reintroduce `@McpNode`.
2. Finish provider discovery so a concrete provider advertises one or more contracts, and make resolver selection fail clearly when zero or multiple candidates satisfy a request. Completed.
3. Extend scanning, generated input schemas, and invocation binding so `@McpService` parameters are internal-only typed injections rather than MCP JSON arguments. Preserve existing `McpCallContext` and progress injection behavior. Completed.
4. Surface tool-level `requires` and provider metadata in the appropriate discovery payloads without changing the `tools/list` contract for existing callers. Keep a separate service listing design. Completed as `services/list`.
5. Define and enforce provider scopes, consumer blacklists, and supplemental access requirements. Preserve cache/replay boundaries so transport results never substitute for live provider identity.
6. Define the module migration map: Nextcloud behavior into its provider artifact, local storage into a provider module, and only cache plus provider-neutral contracts retained natively. Completed: the approved ownership map is in `context.md`.
7. Reconcile the external Nextcloud SDK public API, coordinates, runtime assumptions, and documentation version; choose an adapter/dependency strategy that avoids two competing tool/runtime SPIs. Completed: use `nextcloud-sdk-client:1.0` only as a module-internal client dependency; keep the Meshingress delegated-workspace OCS adapter provider-private and do not import the SDK tool runtime/API/catalog.
8. Extract the Nextcloud provider into `toolspace/nextcloud` with module-owned configuration and auto-configuration; attach it through the distribution once its focused tests pass. Replace server ownership of all Nextcloud-specific classes and endpoints. Completed: the module owns the provider, delegated OCS adapter, viewer state/API, properties, and credential reference; the app no longer contains Nextcloud routing or configuration.
9. Extract local workspace storage into a separate `toolspace/local-storage` provider module, then remove the remaining native lifecycle configuration and every provider-specific `meshingress.storage.*` field. Completed: the module owns local workspace, file, retrieval, cleanup, WebDAV-handoff, web API, scheduling, and property resources; app properties and native storage implementation are removed. `storage/publication-status` now queries registered providers without restoring `ToolStorageRouter`. `LocalStorageProperties` now owns the former binding DTO, so the core configuration library contains neither local-provider values nor their configuration structure.
10. Give injectable capability contracts a common lifecycle and publish provider-owned client input as requirement metadata, separate from callable tool arguments. Completed: `McpServiceLifecycle` supplies optional no-argument `init()`/`stop()` hooks; a concrete provider may declare one typed `init(...)` overload using normal tool-function parameters. Its parameters produce `requirements[requirementKey].inputSchema`; the client submits the matching object in `tools/call.params.requirements[requirementKey]`; invocation binds and calls the typed overload before the tool function and calls `stop()` afterward. Concrete provider configuration migration remains a separate consumer/provider design step.
